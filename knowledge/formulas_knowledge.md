# formulas 説明書

> 対象コード: `supabase/migrations/0002_formulas.sql`, `src/pages/GenreFormulasPage.tsx`, `src/pages/EntriesPage.tsx`, `src/pages/PublicPage.tsx`
> 対象読者: 作成者本人（学習目的）
> 前提知識レベル: アプリ開発初心者（DB・SQL・Reactいずれも初めて）
> 記述方針: 専門用語は初出のたびにかみ砕いて説明する

---

## 0. この文書の読み方・前提知識

- [[entries_list_knowledge|記録一覧説明書]]で説明した「評価軸の名前でマッチングする」という考え方(RLSの範囲とは別に、自分専用のデータを扱うための工夫)。
- 「線形結合」という言葉。中身は単純で、$n \times a + m \times b + l \times c$のように、複数の値にそれぞれ係数(重み)を掛けて足し合わせるだけの式。

### 用語集

| 用語 | 意味（平易な説明） | 初出章 |
|---|---|---|
| 線形結合 | 複数の値に、それぞれ好きな数(重み)を掛けてから全部足し合わせる計算方法 | 1 |
| JSONB | PostgreSQLで、JSON形式のデータ(今回は`{"軸名": 重み}`のようなオブジェクト)をそのまま1つのカラムに保存できる型 | 3 |

---

## 1. このコードで何をするか（概要）

ユーザーが評価軸ごとに好きな重み(係数)を設定し、「重み×スコア」の合計値(線形結合)を計算する「カスタム評価式」を作成・保存できる機能である。作成した式は、自分の記録一覧・公開記録のランキングの両方で、並び替えの基準として使える。

---

## 2. 背景・なぜこれが必要か

ユーザーから「評価軸a, b, cがあったとき、n×a + m×b + l×cのような総合評価を自由に設定し、それで並べたい」という要望があった。

実装にあたり、`(a+b)/c`のような四則演算全般を含む「本当に自由な数式」にするか、`n×a + m×b + l×c`という「重み付きの足し算(線形結合)」だけに絞るかを検討し、後者を選んだ。理由は、前者を実現するには数式文字列を安全に解析する専用の仕組み(簡易的な数式パーサー)を新たに開発する必要があり、実装・テストのコストに見合わないと判断したためである。線形結合だけでも、重みにマイナスの値を使えば「引き算」的な使い方(あるスコアが低いほど高評価、など)も表現できる。

---

## 3. 設計思想・アーキテクチャの考え方

### 3.1 重みを「軸のID」ではなく「軸の名前」で持つ理由

`formulas.weights`は、`{"出汁": 3, "量": -1}`のように、**評価軸の名前**をキーにしたオブジェクトとして保存している。軸のID(`axes.id`)をキーにする方法も考えられたが、以下の理由で名前をキーにした。

1. 同じユーザーが複数のジャンルで同じ軸名(例:「量」)を使っていた場合、同じ式を使い回せる。
2. [[entries_list_knowledge|公開ランキング]]で、**他ユーザーの記録**に自分の式を当てはめたい。他ユーザーの`axes.id`は当然自分のものとは別のIDなので、IDでは絶対に一致しない。一方、`entry_scores.axis_name`は記録作成時点の軸名のスナップショットなので、名前さえ一致すれば、誰の記録にも同じ式を当てはめられる。

この設計は、[[supabase_schema_knowledge|DBスキーマ]]で採用した「スナップショット方式」の考え方をそのまま活用したものである。

### 3.2 formulasテーブルはRLSで完全に本人限定

「他人の記録に自分の式を当てはめられる」と聞くと、逆に「他人が自分の式を覗き見できるのでは」と心配になるかもしれないが、そうはならない。`formulas`テーブル自体は`genres`/`axes`と同じく「常に本人のみが読み書きできる」RLSになっている。他ユーザーは、自分の式を保存・閲覧・使用することしかできない。「自分の基準を、自分が見られる記録(自分の記録＋他人の公開記録)に当てはめて並び替える」という処理は、あくまで**自分のブラウザの中だけ**で完結しており、式そのものがサーバー間でやり取りされることはない。

### 3.3 実装方針: 線形結合のみに絞る

`(a+b)/c`のような数式を許すと、文字列を安全に数値計算に変換する処理(数式パーサー)が必要になる。JavaScriptの`eval()`や`Function()`を使えば簡単に実装できるが、任意の文字列をコードとして実行してしまう危険な方法であり、CLAUDE.mdの「安全なコードを書く」という方針にも反する。今回はこのリスクを避けるため、「軸ごとに数値(重み)を1つ入力する」という単純なUIに絞り、計算は`重み×スコアの合計`という決まった式だけで行う設計にした。

## 4. 実装の考え方（コードと概念の対応）

| 概念 | コード上の対応 | 補足 |
|---|---|---|
| 線形結合の計算 | `scoreByFormula(entry, weights)` | `entry_scores`を軸名でマッチングし、`重み×スコア`を合計 |
| 式の保存 | `formulas`テーブル(`weights`列がJSONB) | 軸名をキーにした重みのマップ |
| 記録一覧での利用 | `EntriesPage`の`sortMode === 'formula_desc'` | 選択中ジャンルの`genre_name`に一致する式だけを候補にする |
| 公開ランキングでの利用 | `PublicPage`の`rankingBasis === 'formula'` | 同じ`scoreByFormula`関数を、他ユーザーの記録にも適用 |

### 主要な設計判断

- **判断**: 重みが設定されていない軸は、計算上「重み0」として扱う
  **理由**: 式を作った後に新しい軸が追加された場合でも、エラーにせず自然に無視できるようにするため
  **他の選択肢**: 未設定の軸があればエラーにする案もあったが、使い勝手を優先した

## 5. コードの読み方（ステップ・バイ・ステップ）

```tsx
function scoreByFormula(entry: EntryWithScores, weights: Record<string, number>) {
  return entry.entry_scores.reduce(
    (sum, s) => sum + (weights[s.axis_name] ?? 0) * s.score,
    0,
  )
}
```

この関数がカスタム評価式の計算の中心である。記録が持つ`entry_scores`(軸ごとのスコア)を1つずつ見て、その軸名に対応する重み(`weights[s.axis_name]`、設定がなければ0)を掛けて、全部足し合わせている。`entry`が誰の記録であっても、`axis_name`という文字列さえ一致すれば計算できる。

```tsx
const { data, error } = await supabase
  .from('formulas')
  .insert({
    owner_id: user.id,
    genre_name: genre.name,
    name: trimmedName,
    weights,
  })
```

`GenreFormulasPage`での保存部分。`weights`はJavaScriptのオブジェクト(`{ "出汁": 3, "量": -1 }`のようなもの)をそのまま渡すだけで、Supabaseのクライアントが自動的にJSON形式に変換してJSONBカラムへ保存してくれる。

## 6. 具体例で動きを追う

1. 「蕎麦」ジャンルで、「コスパ重視」という名前の式を作る。重みは「出汁: 3」「量: 1」「こし: -1」、他の軸は0のまま保存する
2. 記録一覧で「蕎麦」に絞り込み、「カスタム評価式が高い順」→「コスパ重視」を選ぶ
3. 各記録について、`3×出汁のスコア + 1×量のスコア + (-1)×こしのスコア`が計算され、高い順に並び替わる
4. 公開一覧の「ランキング」でも同じ手順で「コスパ重視」を選ぶと、他ユーザーの「蕎麦」ジャンルの公開記録にも同じ計算式が適用され、順位付けされる

---

## 7. つまずきやすいポイント・よくある誤解

- **軸の名前を変更すると、既存の式が静かに効かなくなる**：`weights`のキーは軸名の文字列なので、後から軸名を「こし」→「食感」のように変更すると、古い式の`"こし": -1`という設定は、どの`axis_name`にも一致しなくなり、実質的に無視される(エラーにはならない)。気づきにくい落とし穴のため、11節の限界事項にも記載している。
- **数式パーサーを作らなかったのは手抜きではなく意図的な判断**：`eval()`を使えば四則演算は簡単に実装できるが、任意の文字列をコードとして実行する仕組みは、たとえ自分しか使わないアプリでも避けるべき設計である(3.3節参照)。

## 8. 確認問題

1. `formulas.weights`のキーに`axes.id`ではなく評価軸の「名前」を使っているのはなぜか説明せよ。
   - 解答例: 公開ランキングで他ユーザーの記録にも自分の式を適用したいため。他ユーザーの`axes.id`は自分のものと一致しないが、`entry_scores.axis_name`という名前のスナップショットなら、同じ名前の軸であれば誰の記録にも当てはめられるから。
2. なぜ`(a+b)/c`のような四則演算全般ではなく、重み付き線形結合だけに機能を絞ったのか。
   - 解答例: 任意の数式文字列を安全に計算するには専用の数式パーサーが必要で、`eval()`のような危険な方法を使わずに実装するとコストが大きい。線形結合だけでもマイナスの重みで多くの用途をカバーできるため。
3. 評価軸を後から削除・改名した場合、既存のカスタム評価式にどんな影響があるか。
   - 解答例: `weights`は軸名をキーにしているため、改名すると古いキーがどの軸にも一致しなくなり、その軸の重みは実質0として扱われるようになる(エラーにはならないが、意図しない計算結果になりうる)。
