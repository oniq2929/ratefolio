## 0. この文書の読み方・前提知識

- [[entries_list_knowledge|記録一覧説明書]]で説明した「RLSの許可範囲」と「見せたい範囲」の違い、署名付きURLの考え方。今回はこれを「自分の記録だけ」ではなく「公開されている全ユーザーの記録」に適用する。

### 用語集

| 用語 | 意味（平易な説明） | 初出章 |
|---|---|---|
| フィード | 新しい順にただ流れてくる一覧表示 | 1 |
| ランキング | 何らかの基準で順位付けした一覧表示 | 1 |
| 正規化 | 異なるスケール(5段階評価と10段階評価など)の値を、0〜1のような共通の範囲に変換して比較できるようにすること | 3 |

---

## 1. このコードで何をするか（概要）

全ユーザーが「公開」に設定した記録を、フィード(新着順)またはランキング(スコア順)で閲覧できる画面である。ジャンル絞り込み・キーワード検索にも対応する。

---

## 2. 背景・なぜこれが必要か

引き継ぎ資料の「未決事項」で決めた「公開一覧はフィード/ランキングを切替可能にする」という方針を実現する画面である。これまでの機能(認証・ジャンル管理・記録作成・記録一覧)はすべて「自分のデータ」を扱うものだったが、本機能で初めて「他ユーザーのデータを閲覧する」導線ができる。

## 3. 設計思想・アーキテクチャの考え方

### 3.1 「公開されている記録」をどう絞り込むか

[[entries_list_knowledge|記録一覧]]では「RLSが許可する範囲」から「自分のものだけ」に絞るために`owner_id`を指定した。公開一覧ではその逆で、「RLSが許可する範囲(自分の記録+公開記録)」から「公開記録だけ」に絞るために`.eq('is_public', true)`を明示的に指定している。どちらも「RLSは上限であり、画面が本当に欲しい範囲は別途指定する」という同じ考え方の応用である。

### 3.2 投稿者名の取得は別クエリで行う

`entries`から投稿者の表示名を一度に取得したい場合、通常はテーブル同士の外部キーを使ったJOINで実現する。しかし`entries.owner_id`は`auth.users`を参照しており、`profiles`テーブルも同じく`auth.users`を参照しているだけで、`entries`と`profiles`を直接つなぐ外部キーは存在しない。そのためSupabaseの「埋め込み取得」(`select('*, profiles(...)')`)は使えず、代わりに`entries`取得後に登場した`owner_id`の一覧を集め、`profiles`テーブルに対して`in()`で別途問い合わせている。

### 3.3 ランキングのスコアを「正規化」する理由

ジャンルによって評価スケール(5段階、10段階等)が異なる。異なるスケールの記録を同じランキングで比較するには、スコアをそのまま比べるのではなく、`スコア ÷ そのジャンルのスケール上限`という計算で0〜1の範囲に変換(正規化)してから比較する必要がある。これにより、5段階評価で4点の記録と、10段階評価で8点の記録が、同じ「0.8」として公平に比較できる。

---

## 4. 実装の考え方（コードと概念の対応）

| 概念 | コード上の対応 | 補足 |
|---|---|---|
| 公開記録だけに絞る | `.eq('is_public', true)` | RLSの許可範囲から「公開のみ」をさらに絞り込む |
| 投稿者名の取得 | `owner_id`の重複除去→`profiles`への`in()`問い合わせ | 直接の外部キーがないための代替手段 |
| スコアの正規化 | `score / scaleMax` | 異なる評価スケール同士を比較可能にする |

---

## 5. コードの読み方（ステップ・バイ・ステップ）

```tsx
const ownerIds = [...new Set(fetchedEntries.map((e) => e.owner_id))]
const { data: profiles } = await supabase
  .from('profiles')
  .select('id, display_name')
  .in('id', ownerIds)
```

`Set`を使って重複した`owner_id`を除去したうえで、`profiles`テーブルに対して「このIDのどれかに一致する行」を取得する`in()`検索を行っている。これにより、同じユーザーの記録が何件あっても、`profiles`への問い合わせは1回で済む。

```tsx
const avg =
  entry.entry_scores.reduce((sum, s) => sum + s.score, 0) /
  entry.entry_scores.length
return avg / entry.scale_max
```

「全軸平均」でランキングする場合の計算。まず軸ごとのスコアの単純平均を求め、それをその記録のスケール上限で割ることで正規化している。

---

## 6. 具体例で動きを追う

1. ユーザーA・ユーザーBがそれぞれ「蕎麦」ジャンルの記録を公開している状態で、ユーザーCが公開一覧を開く
2. 「フィード」では、AとBの記録が日付の新しい順に混在して表示される
3. 「ランキング」に切り替え、ジャンルを「蕎麦」に絞ると、AとBの記録の評価軸(名前が一致するもの)で順位付けされる
4. Aが記録を非公開に変更すると、以後の一覧取得でその記録は`is_public = true`の条件に合わなくなり、一覧から消える

---

## 7. つまずきやすいポイント・よくある誤解

- **`entries`と`profiles`は直接JOINできない**：どちらも`auth.users`を参照しているだけで、互いを指す外部キーがないため。3.2節参照。
- **ランキングの正規化を忘れると、評価スケールの違う記録を公平に比較できない**：5段階評価の5点と10段階評価の5点は同じ「5点」でも意味が全く違う。

---

## 8. 確認問題

1. `entries`テーブルから投稿者の表示名を取得するのに、なぜ埋め込み取得(`select('*, profiles(...)')`)が使えないのか説明せよ。
   - 解答例: `entries.owner_id`と`profiles.id`はどちらも`auth.users`を参照しているだけで、`entries`と`profiles`を直接結びつける外部キーが存在しないため。PostgRESTの埋め込み取得は直接のFK関係が必要。
2. ランキングでスコアを`スコア ÷ scale_max`のように正規化しているのはなぜか。
   - 解答例: ジャンルによって評価スケール(5段階、10段階等)が異なるため、そのままの点数では公平に比較できない。0〜1の範囲に揃えることで、異なるスケールの記録同士を比較できるようにするため。
