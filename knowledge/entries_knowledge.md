## 0. この文書の読み方・前提知識

- 三角関数(`cos`/`sin`)を使って、円周上に等間隔で点を配置する考え方。
- SVGの`<polygon>`(多角形)・`<line>`(直線)・`<text>`(文字)という基本図形。

### 用語集

| 用語 | 意味（平易な説明） | 初出章 |
|---|---|---|
| viewBox | SVGの「描画される座標の範囲」を決める属性。この範囲の外に描いたものは、既定では見えなくなる(クリップされる) | 3 |
| ラジアン | 角度の単位。360度 = 2π(=約6.28)ラジアン。JavaScriptの`Math.cos`/`Math.sin`はラジアンで角度を受け取る | 3 |
| text-anchor | SVGの`<text>`要素の属性。文字列を、指定した座標の左揃え/右揃え/中央揃えのどれで描くかを決める | 3 |

## 1. このコードで何をするか（概要）

ジャンルを選び、評価軸ごとにスライダーでスコアを入力すると、その場でレーダーチャート(多角形のグラフ)がリアルタイムに変化して見える記録作成フォームである。任意で写真を1枚添付でき、送信すると`entries`/`entry_scores`テーブル、および写真があればSupabase Storageに保存される。

---

## 2. 背景・なぜこれが必要か

[[genres_knowledge|前回のジャンル管理機能]]で「評価軸は3〜8個」という制限を設けたのは、今回のレーダーチャート表示のためだった。本機能はその約束を実際の画面として実現するものであり、ユーザーから明示的にリクエストのあった「評価軸が5個あったら五角形で、各軸の値で形が変わる」という表示を実装する。

---

## 3. 設計思想・アーキテクチャの考え方

### 3.1 円周上に均等に点を配置する考え方

n個の軸を、円の中心から見て均等な角度で並べたい。1周(360度 = $2\pi$ラジアン)をn個に分けるので、i番目(0始まり)の軸の角度は

$$\text{angle}_i = -\frac{\pi}{2} + i \times \frac{2\pi}{n}$$

となる。`-π/2`(-90度)から始めているのは、「1番目の軸が真上に来るように」したいためである(時計の12時の位置に相当)。あとは`Math.cos(angle)`/`Math.sin(angle)`を使えば、角度から中心を基準にした`(x, y)`が求まる。これは高校数学の「単位円上の点 = (cosθ, sinθ)」の考え方そのものである。

### 3.2 スコアを「半径」に変換する

各軸の頂点は、スコアが高いほど中心から遠く(外側)に来るようにしたい。スコア`score`・スケール上限`scaleMax`・チャートの最大半径`maxRadius`から、

$$\text{radius} = \frac{\text{score}}{\text{scaleMax}} \times \text{maxRadius}$$

という比例計算で、実際に描画する半径を求めている。5段階評価でスコア4なら、`(4/5) × maxRadius`の位置に頂点が来る。

### 3.3 ラベルの向きをコサインで判定する

軸の名前(「こし」等)を、頂点の外側に文字で表示している。円の右半分にある軸は文字を左揃え(`text-anchor: start`)、左半分にある軸は右揃え(`end`)、真上・真下に近い軸は中央揃え(`middle`)にすると、文字が頂点からはみ出さずきれいに並ぶ。「右半分か左半分か」は、その角度のコサイン(`cos`)の符号で判定できる(コサインが正なら右側、負なら左側)。

### 3.4 写真アップロードの設計

写真は、[[supabase_schema_knowledge|前回のDBスキーマ]]で決めた「Storageのパスは`{owner_id}/{entry_id}.拡張子`」という命名規則に従ってアップロードする必要がある。ところが通常、`entries`テーブルの`id`はDB側が自動生成するため、INSERTするまで値が分からない。

そこで、`entries`にINSERTする**前**に、ブラウザ側で`crypto.randomUUID()`を使って`id`をあらかじめ作り、それをアップロード先のパスにも、INSERT時の`id`にも両方使うようにした。こうすることで、「先に写真をアップロード→そのパスを持たせて記録を作成」という順番が成立する。

写真のプレビューには、Supabaseにアップロードした結果を待たず、`URL.createObjectURL(file)`というブラウザ標準の機能を使っている。これは「選んだファイルを、まだどこにも送信せずにその場で表示できるURL」を作る仕組みで、通信を待たずに即座にプレビューできる利点がある。

### 3.5 実際に起きた不具合: SVGのクリップ

実装後の動作確認で、5軸中「こし」の数値だけがラベルに表示されない、という不具合が発生した。原因は、SVGのルート要素が**既定で`overflow: hidden`**であり、`viewBox`の範囲外に描いた文字が切り取られてしまうことだった。ラベルの座標(`maxRadius + 16`の位置)に文字の横幅を足すと、ちょうど「こし」の位置(円の右側で`text-anchor: start`)だけが`viewBox`の右端(200px)を超えてしまっていた。

対処として、SVG要素に`style={{ overflow: 'visible' }}`を指定し、`viewBox`の外に出た部分もそのまま描画されるようにした。修正前後の比較図は[[entries_report|報告書]]を参照。

## 4. 実装の考え方（コードと数式・概念の対応）

| 数式・概念 | コード上の対応 | 補足 |
|---|---|---|
| $\text{angle}_i = -\pi/2 + i \times 2\pi/n$ | `angleForIndex(index)` | `axes.length`がn |
| 極座標→直交座標変換 | `pointAt(radius, index)` | `center + radius * cos/sin` |
| スコア→半径の比例計算 | `pointAt((axis.score / scaleMax) * maxRadius, i)` | データ多角形の頂点計算 |
| ラベルの左右揃え判定 | `cos > 0.3 ? 'start' : cos < -0.3 ? 'end' : 'middle'` | 0.3という閾値は、真上・真下付近では中央揃えにするための余裕 |

### 主要な設計判断

- **判断**: 目盛りの同心多角形を、`scaleMax`の整数値ごとではなく、外周に対する割合(1/3, 2/3, 1)で描いた
  **理由**: `scaleMax`が5でも10でも見た目のバランスが変わらないようにするため。整数値ごとに描くと10段階評価のときに線が密集しすぎる

- **判断**: ライブラリを追加せず、SVGを直接手書きした
  **理由**: 三角関数さえ分かれば実装できる程度の複雑さであり、[[genres_knowledge|前回]]決めた方針(新規ライブラリを増やさない)と一致する

- **判断**: `entries.id`をDBの自動生成に任せず、クライアント側で`crypto.randomUUID()`により先に生成した
  **理由**: Storageへのアップロードパスに`entry_id`を含める命名規則にしているため、INSERT前にIDが確定している必要がある
  **他の選択肢**: 先にDBへ`photo_path`なしでINSERTしてIDを取得し、アップロード後に`update`で`photo_path`を追記する方法もあったが、往復が1回増えるため採用しなかった

## 5. コードの読み方（ステップ・バイ・ステップ）

```tsx
const angleForIndex = (index: number) =>
  -Math.PI / 2 + (index * 2 * Math.PI) / axes.length

const pointAt = (radius: number, index: number) => {
  const angle = angleForIndex(index)
  return {
    x: center + radius * Math.cos(angle),
    y: center + radius * Math.sin(angle),
  }
}
```

角度を求める関数と、「角度・半径→座標」に変換する関数。この2つを組み合わせるだけで、目盛り線・軸線・データ多角形・ラベルの座標すべてを計算している。

```tsx
<svg
  viewBox={`0 0 ${size} ${size}`}
  width={size}
  height={size}
  style={{ overflow: 'visible' }}
>
```

3.5節で説明した不具合の修正箇所。`overflow: visible`がないと、`viewBox`の外に描いた文字が切り取られる。

```tsx
<input
  type="range"
  min={1}
  max={selectedGenre.scale_max}
  step={1}
  value={scores[axis.id] ?? defaultScoreFor(selectedGenre.scale_max)}
  onChange={(e) =>
    setScores((prev) => ({ ...prev, [axis.id]: Number(e.target.value) }))
  }
/>
```

`NewEntryPage`側。スライダーの値が変わるたびに`scores`(軸IDをキーにしたスコアの一覧)を更新し、その状態をそのまま`RadarChart`に渡すことで、動かすたびにチャートが再描画される。

## 6. 具体例で動きを追う

1. 「蕎麦」ジャンル(5段階評価、軸: 香り/こし/天ぷら/出汁/量)を選択する
2. 各軸のスコアが初期値(3段階目あたり)で並び、五角形のチャートが表示される
3. 「出汁」のスライダーを4に動かすと、`scores`の該当キーだけが更新され、5番目の頂点(出汁の方向)だけが外側に伸びる
4. 「記録する」を押すと、`entries`に1行、`entry_scores`に5行保存され、保存直後のスコアで描いたチャートが確認パネルに表示される

## 7. つまずきやすいポイント・よくある誤解

- **SVGは既定で`overflow: hidden`**：`viewBox`の外に描画したものは、明示的に`overflow: visible`を指定しない限り見えない。円グラフ・レーダーチャートのように、ラベルが円の外側にはみ出すタイプの図では特に注意が必要(3.5節で実際に遭遇した)。
- **JSXで`{値}`が`undefined`のとき、その部分だけ何も描画されない**：たとえば`{name}({score})`で`score`が`undefined`だと、括弧だけが残って`name()`のように表示される。今回、送信直後の確認パネル用のスコアに`?? defaultScoreFor(...)`という保険を入れ忘れていたことに気づき、スライダー側の表示と揃えて修正した。
- **`scores`をオブジェクトのスプレッド(`{ ...prev, [id]: value }`)で更新しているのは、他の軸のスコアを消さないため**：`setScores(initialScores)`のように丸ごと置き換えるのはジャンル切り替え時だけで、1軸だけ更新するときは必ず既存の値を保持する。
- **`<input type="file">`は見た目が地味で押せると気づきにくい**：ブラウザ標準の「ファイルを選択」ボタンは装飾がなく、実機確認で「押せるか分かりにくい」との指摘があった。Tailwindの`file:`バリアント(`file:bg-neutral-900`等)で、疑似要素的にボタンらしい見た目を付けられる。
- **`<input type="file">`は値をReactの`state`で完全にコントロールできない**：同じファイルを選び直しても`onChange`が発火しないことがあるため、写真を削除するときはReactのstateだけでなく、`ref`経由で実際のDOM要素の`value`も空文字にリセットする必要がある。

## 8. 確認問題

1. なぜ最初の軸(index = 0)の角度を`0`ではなく`-π/2`にしているか説明せよ。
   - 解答例: 角度0のままだと1番目の軸が円の右側(3時の位置)に来てしまう。真上(12時の位置)から描き始めたいので、90度(`π/2`)分だけ回転させている。
2. `text-anchor`の判定にコサインを使っているのはなぜか。
   - 解答例: コサインは「その角度が単位円上でどれだけ右(正)/左(負)に寄っているか」を表す値だから。右寄りの軸は文字を左揃えにして頂点から右へ伸ばし、左寄りの軸は右揃えにして頂点から左へ伸ばすと、文字が頂点と重ならずに配置できる。
3. 「こし」の数値だけが表示されない不具合の原因と、その直し方を説明せよ。
   - 解答例: SVGは既定で`viewBox`の外側をクリップして表示しないため、ラベルの座標が`viewBox`の端を超えていた「こし」の数値部分だけが切り取られていた。`<svg>`に`style={{ overflow: 'visible' }}`を指定することで解決した。
4. 写真アップロードの際、なぜ`entries.id`をDBに生成させず、あらかじめクライアント側で作っているのか説明せよ。
   - 解答例: Storageのアップロード先パスに`entry_id`を含める命名規則になっており、`entries`へのINSERTより前にパスを確定させて写真をアップロードする必要があるため。DBの自動生成に任せると、INSERT後でないとIDが分からず、先に写真をアップロードできない。
