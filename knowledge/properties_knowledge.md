## 0. この文書の読み方・前提知識

- [[entries_knowledge|記録作成の説明書]]の、写真を先に圧縮してStorageへ送る流れ。今回はその流れを速くしている。

### 用語集

| 用語 | 意味（平易な説明） | 初出章 |
|---|---|---|

## 1. このコードで何をするか（概要）

ジャンルごとに「都道府県」「店」「温度」「純米/大吟醸」のような**プロパティ**を自由に定義し、記録ごとに値を入れられるようにした。あわせて、記録の保存にかかる待ち時間を短くし、一部の端末で写真の追加に失敗する不具合を修正した。

---

## 2. 背景・なぜこれが必要か

- これまでの記録は「評価軸のスコア」「タグ」「コメント」しか持てず、「どこの県のお酒か」「何度で飲んだか」のような**分類・条件の情報**を構造的に残せなかった。タグでも代用できるが、「温度が10℃以下」のような数値の比較や、日本地図への集計には使えない。
- 「保存ボタンを押してから完了までが遅い」という声があった。調べると、写真の縮小 → 写真のアップロード → 記録の保存 → スコアの保存、と**4つの処理を1つずつ順番に待っていた**。
- 「写真の追加で不具合がある（自分のiPhoneでは問題ない）」という報告があった。端末が特定できなかったため、端末による違いが出やすい箇所をまとめて対策した。

---

## 3. 設計思想・アーキテクチャの考え方

### 3.1 プロパティは「定義」と「値」を分けて持つ

![プロパティの保存構造](../figures/properties_result.svg)

- **定義**（`genre_properties`テーブル）: 「日本酒ジャンルには、都道府県（都道府県型）・種類（選択肢型）・温度（数値型）がある」という**設計図**。評価軸（`axes`）と同じく、本人しか読み書きできない。
- **値**（`entries.properties`列）: 記録1件ごとの `[{name:"都道府県", type:"prefecture", value:"新潟県"}, ...]`。**名前と型ごとコピー（スナップショット）**して保存する。

なぜコピーするのか。評価軸名と同じで、あとで定義の名前を変えたり消したりしても、**過去の記録の内容が勝手に変わらない**ようにするためである。また、値が`entries`の行の中にあるので、`entries`のRLS（公開/非公開のルール）がそのまま効く。プロパティ専用の公開ルールを別に書かなくてよいので、「非公開の値が他人に見える」事故が起きにくい。

### 3.2 型（Obsidianのプロパティ型にならった5種類）

| 型 | 入力欄 | 使い道 |
|---|---|---|
| テキスト | 自由入力 | 店名など |
| 数値 | 数値キーボード | 温度・価格。「10以下」のような比較ができる |
| 選択肢 | プルダウン | 純米／吟醸／大吟醸など、候補を決めておく |
| 都道府県 | 47都道府県のプルダウン | 日本地図での集計 |
| 国 | 約250か国のプルダウン | 世界地図での集計（ワインなど） |

都道府県・国は「選択肢型の特別版」で、候補があらかじめ用意されている。表記ゆれ（「新潟」と「新潟県」など）が起きないので、地図に正しく集計できる。

### 3.3 保存を速くした2つの工夫

![記録保存の処理フロー](../figures/properties_flowchart.svg)

1. **写真の縮小を「選んだ瞬間」に始める**: 写真を選ぶと裏で縮小処理が始まり、その結果（Promise）を`useRef`に預けておく。ユーザーがコメントなどを入力している間に縮小が終わるので、保存ボタンを押したときには待たずに済むことが多い。
2. **独立した処理を同時に送る**: 写真のアップロードと記録の保存は、互いの結果を待つ必要がない（写真のファイル名は端末で先に決めた`entryId`から作れる）。`Promise.all`で同時に送ると、待ち時間は「2つの合計」ではなく「遅いほう」だけになる。さらに、記録とスコアの保存はDB関数`create_entry`にまとめ、**通信1回**にした。

DB関数の中は1つのトランザクションなので、スコアの保存に失敗すれば記録の保存も自動で取り消される。これまでアプリ側で書いていた「失敗したら記録を消す」という後片付けが不要になった。

### 3.4 DB関数でも安全性を保つ

`create_entry`は`security invoker`（呼び出した人の権限で動く）にしている。そのため、関数の中でもRLSがそのまま効き、他人の記録を書き換えることはできない。また、`owner_id`はアプリから送られた値を使わず、DB側で`auth.uid()`（ログイン中の本人のID）を入れる。アプリから送る値は改ざんされうるので、「誰の記録か」はDBに決めさせる。

### 3.5 写真の不具合への対策

原因が特定できなかったため、端末によって違いが出る箇所を洗い出して、すべてに対策した。

| 起こりうること | 対策 |
|---|---|
| ファイルの種類（`file.type`）が空で届く（Androidの一部ギャラリー） | 空なら画像とみなして処理する。保存時は拡張子から種類を推定する |
| `createImageBitmap`が使えない／失敗する（古いiOS） | `<img>`要素で読み込み直す |
| HEIC形式が他のブラウザで表示できない | 縮小できた場合は必ずJPEGで保存する |
| 縮小に失敗し、元の写真が5MBを超える | 形式とサイズを含む日本語のエラーを出す |
| 編集画面で、写真のなかった記録に写真を付けると権限エラー | Storageの閲覧ルールに「自分のフォルダ」を追加。さらに上書き保存をやめ、毎回別のファイル名で保存する |

最後の項目は特に有力な原因である。上書き保存（upsert）は「既存ファイルを見る権限」も必要とするが、旧ルールは「記録に登録済みの写真」しか見られなかった。そのため、まだ記録に登録していない新しい写真の上書きが拒否される場合があった。

## 4. 実装の考え方（コードと概念の対応）

| 概念 | コード上の対応 | 補足 |
|---|---|---|
| プロパティの定義 | `genre_properties`テーブル / `GenreProperty`型 | RLSは評価軸と同じく「ジャンルの持ち主のみ」 |
| プロパティの値 | `entries.properties`（JSONB）/ `EntryProperty`型 | 未入力の項目は保存しない |
| 入力欄1行分 | `PropertyField`（`buildPropertyFields`で作る） | 定義と保存済みの値を合わせたもの |
| 型ごとの候補 | `choicesFor()` | 選択肢・都道府県・国は候補を返し、テキスト・数値は`null` |
| 保存を1回の通信に | `create_entry` / `update_entry`（SQL関数） | `supabase.rpc()`で呼ぶ |
| 写真の事前縮小 | `compressedPhotoRef`（`useRef`） | 再描画の対象にならない入れ物 |

### 主要な設計判断
- **判断**: プロパティの値を、別テーブルではなく`entries`のJSONB列に保存した
  **理由**: 公開/非公開のRLSを新たに書かずに済み、1回の取得で値も揃う。件数が少ない個人の記録では、検索もアプリ側で十分に速い
  **他の選択肢**: `entry_properties`テーブルを作る（DB側で検索しやすいが、RLSの書き漏れの危険が増える）
- **判断**: 編集画面では写真のアップロードを先に済ませてから記録を更新する（同時にはしない）
  **理由**: 同時に送ると、記録が「まだ存在しない写真」を指す瞬間ができ、一覧で一瞬画像が表示されない可能性がある
- **判断**: 前回選んだジャンルを端末（localStorage）に覚え、次回は自動で選んでおく
  **理由**: 同じジャンルを続けて記録することが多く、選び直す手間が「登録の遅さ」として感じられるため

## 5. コードの読み方（ステップ・バイ・ステップ）

```tsx
// NewEntryPage.tsx: 写真を選んだ瞬間に縮小を始めておく
compressedPhotoRef.current = file ? compressImage(file) : null
compressedPhotoRef.current?.catch(() => {})
```

`compressImage(file)`は、呼んだ瞬間に処理を始め、「あとで結果が届く約束（Promise）」をすぐ返す。その約束を`useRef`に預けておく。`.catch(() => {})`は、失敗しても「誰も受け取らないエラー」として警告が出ないようにするためのもの。保存時には改めて`await`し、失敗していればそこで日本語のエラーを出す。

```tsx
// 写真のアップロードと記録の保存を同時に送る
const [uploadRes, entryRes] = await Promise.all([
  supabase.storage.from('entry-photos').upload(photoPath, ...),
  supabase.rpc('create_entry', { p_entry: {...}, p_scores: [...] }),
])
```

2つの通信を同時に送り、両方の結果が揃うまで待つ。片方だけ失敗した場合は、成功したほうを消して、「写真だけ」「記録だけ」が残らないようにしている。

```sql
-- create_entry の中: owner_id はアプリから受け取らず auth.uid() を使う
insert into public.entries (id, owner_id, ...) values (v_id, auth.uid(), ...);
insert into public.entry_scores (...) select ... from jsonb_array_elements(p_scores) as s;
```

`jsonb_array_elements`は、JSONの配列を1行ずつに展開するPostgreSQLの関数。評価軸のスコアをまとめて受け取り、1つの`insert`で全行を入れている。

## 6. 具体例で動きを追う

日本酒ジャンルに「都道府県（都道府県型）」「種類（選択肢: 純米, 吟醸, 大吟醸）」「温度（数値）」「店（テキスト）」を定義したとする。

1. 記録作成画面で日本酒を選ぶと、`buildPropertyFields`が4行分の入力欄を作る（値はすべて空）。
2. 写真を選ぶ → 裏で縮小開始（例: 4.2MBのHEIC → 0.3MBのJPEG）。
3. 都道府県「新潟県」、種類「大吟醸」、温度「10」を入力し、店は空のまま「記録する」。
4. `fieldsToEntryProperties`が、空の「店」を除いた3件を `[{name:"都道府県",type:"prefecture",value:"新潟県"}, {name:"種類",type:"select",value:"大吟醸"}, {name:"温度",type:"number",value:10}]` にする（温度は文字列ではなく数値の10になる）。
5. 写真のアップロードと`create_entry`が同時に送られ、両方成功 → 完了表示。

## 7. つまずきやすいポイント・よくある誤解

- **「プロパティ名を変えたら過去の記録も変わる」わけではない**: 値はスナップショットなので、過去の記録には旧名のまま残る。編集画面では、旧名の値も消えずに表示される（`buildPropertyFields`が保存済みの値も拾うため）。
- **DB関数を作っただけではアプリから呼べない**: `grant execute ... to authenticated`で、ログインユーザーに実行を許可する必要がある。逆に未ログイン（`anon`）からは`revoke`で呼べないようにしている。
- **migrationの適用を忘れると保存できない**: `create_entry`はDB側に作る関数なので、`0005`のSQLをSupabaseで実行する前に新しいアプリを公開すると、記録の保存が失敗する。

## 8. 確認問題

1. プロパティの値を`entries`の中に保存すると、公開/非公開の扱いで何がうれしいか。
   - 解答: `entries`のRLSがそのまま効くので、プロパティ専用の公開ルールを書かなくても、非公開記録の値は他人に見えない。
2. 写真のアップロードと記録の保存を`Promise.all`で同時に送れるのはなぜか。
   - 解答: 写真のファイル名に使う`entryId`を端末で先に決めているので、互いの結果を待つ必要がないから。
3. `create_entry`で`owner_id`を`auth.uid()`にしているのはなぜか。
   - 解答: アプリから送られる値は改ざんできるため。「誰の記録か」はDBがログイン情報から決める。
4. 編集画面で写真を上書き（upsert）せず、毎回別名で保存するようにした理由を2つ挙げよ。
   - 解答: (1) 上書きには既存ファイルの閲覧権限も必要で、権限エラーになりやすい。(2) 同じURLだと古い画像がキャッシュで表示され続けることがある。
