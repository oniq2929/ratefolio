|---|---|---|

| 入れ子ルート(nested route)のレイアウト | 複数の画面に共通する外枠(ヘッダー等)を1箇所にまとめ、`<Outlet />`でその中に各画面を差し込む構成 | 3 |

## 1. このコードで何をするか（概要）

自分が作った記録を一覧表示し、ジャンルでの絞り込み・キーワード検索・並び替え(日付順、または特定の評価軸のスコアが高い順)ができる画面である。あわせて、どのページからでもトップページに戻れる共通ヘッダーを追加した。

---

## 2. 背景・なぜこれが必要か

これまでの機能(認証・ジャンル管理・記録作成)は「データを作る」側だけだった。作った記録を見返せなければ記録アプリとして機能しないため、一覧画面が必要になる。

また、ユーザーから「特定の評価軸を基準に並べたい」という要望があった。たとえば「今まで食べた蕎麦を、出汁の評価が高い順に見たい」というような使い方を想定している。

加えて、動作確認中に「トップページに戻る手段がない」という指摘があり、共通ヘッダーを追加することになった。

---

## 3. 設計思想・アーキテクチャの考え方

### 3.1 RLSは「見てよい範囲」であって「見たい範囲」ではない

[[supabase_schema_knowledge|前回]]設計した`entries_select_own_or_public`ポリシーは、「自分の記録」と「他人の公開記録」の両方を読むことを許可している。これは、将来作る「公開一覧」機能のために必要な設計である。

しかし今回の「自分の記録一覧」では、他人の公開記録は混ぜたくない。そこで、`.from('entries').select(...)`だけでなく、`.eq('owner_id', user.id)`を明示的に付け足している。RLSは「許可される範囲の上限」を決めるだけであり、「今欲しいデータの範囲」に自動で絞ってくれるわけではない、という点を意識する必要がある。

### 3.2 非公開Storageの写真を見るための「署名付きURL」

記録作成時にアップロードした写真は、非公開バケット(`entry-photos`)に入っている。ブラウザで直接`https://.../entry-photos/xxx.jpg`のようなURLを開いても、認証情報がなければ弾かれる。

そこで、Supabaseの`createSignedUrls()`という機能を使い、「あなたが今ログインしていて、かつこの写真を見る権限がある」ことを確認したうえで、一定時間(今回は60分)だけ有効な特別なURLを発行してもらう。このURLなら`<img src="...">`にそのまま使える。写真が複数あっても、1回のAPI呼び出しでまとめてURLを発行できるようにしている(1枚ずつ問い合わせると、写真の枚数だけ通信が発生してしまう)。

### 3.3 絞り込み・並び替えをクライアント側で行う理由

ジャンル絞り込み・キーワード検索・並び替えは、すべて一度取得したデータに対してJavaScript側(`Array.prototype.filter`/`sort`)で行っている。Supabaseへ条件ごとに問い合わせ直す方法もあるが、個人の記録アプリでは件数がそれほど多くならないと想定し、シンプルさを優先した。件数が非常に多くなった場合は、DB側の検索(`ilike`によるあいまい検索等)に切り替える余地がある。

### 3.4 評価軸での並び替えは、ジャンルを1つに絞っているときだけ

評価軸はジャンルごとに異なる(「蕎麦」の「出汁」と「ラーメン」の「スープ」は別の軸)。複数ジャンルが混在した状態で「軸で並び替え」を選べるようにすると、比較のしようがない軸同士を無理やり並べることになる。そのため、ジャンルを1つに絞り込んでいるときだけ、そのジャンルの軸一覧から並び替え基準を選べるようにしている。

### 3.5 共通ヘッダーを`AppLayout`にまとめる

[[genres_knowledge|前回]]、ログイン必須判定を`RequireAuth`にまとめたのと同じ考え方で、「Ratefolioロゴ(トップへのリンク)とログアウトボタン」という共通のヘッダーを`AppLayout`という1つのコンポーネントにまとめた。React Routerの入れ子ルートを使い、`RequireAuth`の内側にさらに`AppLayout`を挟むことで、ログイン必須ページすべてに自動で同じヘッダーが付くようになる。各ページ(`HomePage`等)は、もう自分でヘッダーを描画する必要がない。

## 4. 実装の考え方（コードと概念の対応）

| 概念 | コード上の対応 | 補足 |
|---|---|---|
| 自分の記録だけに絞る | `.eq('owner_id', user.id)` | RLSだけに頼らず明示的に指定 |
| 写真の表示権限確認 | `supabase.storage.from('entry-photos').createSignedUrls(...)` | 60分間有効なURLをまとめて発行 |
| 軸で並び替え時、スコア未設定の記録の扱い | `?? -1`で最下位扱い | ジャンル変更等で軸構成がずれた場合の保険 |
| 共通ヘッダー | `AppLayout` + `<Outlet />` | `RequireAuth`と同じ入れ子ルートの考え方 |

### 主要な設計判断

- **判断**: 検索・絞り込み・並び替えをクライアント側で行った
  **理由**: 個人の記録アプリとしては件数が少なく、DB問い合わせを複雑にするメリットが薄い
  **他の選択肢**: 件数が増えたら、Supabaseの`ilike`検索や`order`をサーバー側で組み合わせる方式に切り替える

## 5. コードの読み方（ステップ・バイ・ステップ）

```tsx
supabase
  .from('entries')
  .select('*, entry_scores(*)')
  .eq('owner_id', user.id)
  .order('entry_date', { ascending: false })
```

自分の記録だけを、紐づく`entry_scores`(軸ごとのスコア)込みで取得する。`.eq('owner_id', user.id)`が3.1節で説明した「自分のものだけに絞る」ための1行である。

```tsx
const { data: signedUrls } = await supabase.storage
  .from('entry-photos')
  .createSignedUrls(photoPaths, 60 * 60)
```

写真パスの配列(`photoPaths`)をまとめて渡し、60×60秒(1時間)有効な署名付きURLを一括発行する。戻り値は各パスに対応するURLの配列になる。

```tsx
if (sortMode === 'axis_desc' && sortAxisId) {
  const scoreOf = (entry: EntryWithScores) =>
    entry.entry_scores.find((s) => s.axis_id === sortAxisId)?.score ?? -1
  sorted.sort((a, b) => scoreOf(b) - scoreOf(a))
}
```

選んだ軸(`sortAxisId`)に対応するスコアを各記録から取り出し、降順(`b - a`)に並べ替える。該当する軸のスコアが見つからない記録は`-1`扱いにして、一覧の最後に回す。

## 6. 具体例で動きを追う

1. 「蕎麦」ジャンルの記録が3件、「ラーメン」ジャンルの記録が2件ある状態で一覧を開く → 5件すべてが日付の新しい順に並ぶ
2. ジャンルを「蕎麦」に絞り込む → 蕎麦の3件だけが表示され、「並び替え」に軸選択が現れる
3. 並び替えを「特定の評価軸が高い順」、軸を「出汁」に設定する → 3件が出汁のスコアが高い順に並び替わる
4. キーワード欄に「大盛り」と入力する → タグまたはコメントに「大盛り」を含む記録だけに絞られる

## 7. つまずきやすいポイント・よくある誤解

- **RLSで見えることと、欲しいデータの範囲は別**：3.1節参照。「自分のデータだけ」を意図する画面では、`owner_id`等の条件を必ず自分で付け加える。
- **署名付きURLには有効期限がある**：今回は60分に設定しているため、一覧画面を開いたまま1時間以上経つと、画像が表示できなくなる可能性がある(11節の限界事項に記載)。
- **並び替えの基準にした軸のIDが、記録によっては存在しないことがある**：ジャンルの軸を後から追加・削除した場合、古い記録の`entry_scores`にはその軸のスコアがない。今回は「見つからなければ最下位」という扱いにしているが、ユーザーからは理由が分かりにくい可能性がある。

## 8. 確認問題

1. `entries_select_own_or_public`というRLSポリシーがあるにもかかわらず、`EntriesPage`でなぜ`.eq('owner_id', user.id)`を追加しているのか説明せよ。
   - 解答例: RLSは「他ユーザーの公開記録も読んでよい」という許可を与えているだけであり、「自分の記録だけ」を取り出したい今回の画面では、その許可の範囲の中からさらに自分でowner_idを条件に絞り込む必要があるため。
2. 写真の表示に、Storageの公開URL(`getPublicUrl`)ではなく署名付きURL(`createSignedUrl`)を使っているのはなぜか。
   - 解答例: `entry-photos`バケットは非公開設定であり、`getPublicUrl`は誰でもアクセスできる前提のURLしか作れない。非公開のファイルを、権限のある人にだけ一時的に見せるには署名付きURLが必要。
3. 評価軸での並び替えが、ジャンルを1つに絞り込んでいるときしか使えないのはなぜか。
   - 解答例: 評価軸はジャンルごとに異なる構成であり、たとえば「蕎麦の出汁」と「ラーメンのスープ」を同じ物差しとして並べることに意味がないため。
