## 1. このコードで何をするか（概要）

ユーザーが自分のジャンル(例:「蕎麦」)を、評価スケール(何段階評価か)と評価軸(3〜8個、例:「コシ」「出汁」)とセットで作成・一覧表示・削除できる画面のコードである。

---

## 2. 背景・なぜこれが必要か

Ratefolioの中核は「ジャンルごとに評価軸をn個自由に設定できる」ことである。この画面がなければ、[[supabase_schema_knowledge|前回作った]]`genres`/`axes`テーブルにデータを入れる手段がなく、記録(entries)を作ることもできない。

また、今回のユーザーとの会話で「評価をレーダーチャート(多角形)で描画したい」という要望が出た。多角形は最低3つの頂点がないと面積のある形にならない(2点だと線、1点だと点になってしまう)ため、**評価軸の数を3〜8個に制限する**という設計判断につながっている。

---

## 3. 設計思想・アーキテクチャの考え方

（このプロジェクトには数式は出てこないため、この章は「なぜこの設計にしたか」という考え方の説明に読み替えている）

### 3.1 なぜ評価軸を3〜8個に制限するか

レーダーチャートは、軸の数だけ頂点を持つ多角形として評価を表現する。軸が1〜2個だと、幾何学的に「多角形」にならない(1個は点、2個は線分)。逆に軸が多すぎると(10個以上など)、1つ1つの頂点が詰まって見づらくなる。3〜8個という範囲は、「多角形として意味を持つ最小値」と「見やすさが保てる現実的な最大値」の両方を満たす値として決めた。

この制約は、実際にチャートを描く機能(今後の記録作成画面)を作る前の、**入り口となるデータ作成画面の時点で先に制限しておく**という考え方に基づく。あとから既存データの軸数を制限しようとすると、既に2軸や10軸で作られたジャンルの扱いに困るため、最初から範囲内でしか作れないようにする方が安全である。

### 3.2 `RequireAuth`という共通の門番

[[auth_knowledge|前回]]は`HomePage`だけに「ログインしていなければ`/login`へ」という判定を書いていたが、`GenresPage`・`NewGenrePage`が増えたことで同じ判定が複数箇所に重複しそうになった。

そこで、React Routerの「入れ子ルート(nested routes)」という機能を使い、`RequireAuth`という1つのコンポーネントに判定をまとめた。`<Route element={<RequireAuth />}>`の内側に置いたページはすべて自動的にログイン必須になり、各ページ自身はログイン判定を書かなくてよくなる。`RequireAuth`の中の`<Outlet />`は「ここに、内側のルートで指定された実際のページを描画する」という目印である。

### 3.3 ジャンルと軸を2回に分けてINSERTする理由と限界

`genres`に1行作ってから、その`id`を使って`axes`に複数行作る、という2段階の処理になっている。本来、両方が「両方成功する」か「両方失敗する」かのどちらかになる(トランザクション)のが理想だが、Supabaseの通常のクライアントAPIから直接複数テーブルへのトランザクションを組むことはできない(Postgresの関数(RPC)を別途書けば可能)。

今回は影響範囲が小さい(ジャンル作成1回分)ため、簡易的な対処として「`axes`の作成に失敗したら、直前に作った`genres`の行を削除する」という後片付け処理を入れている。完全なトランザクションではないが、実用上は「軸のない空ジャンルが残る」という中途半端な状態を避けられる。

## 4. 実装の考え方（コードとテーブル設計の対応）

| 概念 | コード上の対応 | 補足 |
|---|---|---|
| 評価軸3〜8個の制限 | `NewGenrePage`の`MIN_AXES`/`MAX_AXES`定数、追加/削除ボタンの`disabled`制御 | DB側には範囲チェックの制約はなく、アプリ側のみで担保している |
| ジャンルと軸をまとめて取得 | `GenresPage`の`.select('*, axes(*)')` | 外部キー(`axes.genre_id → genres.id`)をもとに、SupabaseのAPIが自動でJOINしてくれる |
| ログイン必須ページの共通化 | `RequireAuth` + React Routerの入れ子ルート | 新しい保護ページを増やしても、`App.tsx`にルートを1行足すだけでよい |

### 主要な設計判断

- **判断**: 評価軸の数の制限(3〜8)をDBの制約ではなくアプリ側のUIで実装した
  **理由**: 「あるジャンルに紐づく軸の行数が3〜8個であること」はPostgreSQLのCHECK制約(1行単位の条件式)では直接表現できず、実現にはトリガー関数が必要になる。現状はこの画面からしかジャンルを作らないため、UI側での制限で十分と判断した
  **他の選択肢**: 将来、他の経路(APIの直接呼び出し等)からもジャンルが作られるようになった場合は、DBトリガーでの二重チェックを検討する

## 5. コードの読み方（ステップ・バイ・ステップ）

```tsx
const { data: genre, error: genreError } = await supabase
  .from('genres')
  .insert({ owner_id: user.id, name: trimmedName, scale_max: scaleMax })
  .select()
  .single()
```

`genres`テーブルへの登録。`.select().single()`を付けることで、INSERTした行そのもの(特に自動生成された`id`)を戻り値として受け取れる。この`id`が次の`axes`登録で必要になる。

```tsx
const { error: axesError } = await supabase.from('axes').insert(
  trimmedAxes.map((axisName, index) => ({
    genre_id: genre.id,
    name: axisName,
    sort_order: index,
  })),
)
```

配列を渡すと、Supabaseは複数行を1回のリクエストでまとめて登録してくれる。`sort_order`に配列のインデックス(0, 1, 2...)をそのまま使うことで、入力した順番を保持している。

```tsx
supabase
  .from('genres')
  .select('*, axes(*)')
  .order('created_at', { ascending: false })
```

`GenresPage`での取得部分。`axes(*)`という書き方だけで、外部キーで繋がった`axes`テーブルの行を、対応する`genres`の行にネストした配列として一緒に取得できる。フロントエンド側で別途`axes`テーブルに問い合わせる必要がない。

## 6. 具体例で動きを追う

1. ユーザーが「蕎麦」「5段階評価」、軸「香り」「こし」「天ぷら」「出汁」「量」(5個)を入力して送信
2. `genres`に1行作成される(`scale_max = 5`)
3. `axes`に5行作成される(`sort_order`が0〜4、それぞれ`genre_id`が手順2のIDを指す)
4. `/genres`に遷移し、`select('*, axes(*)')`で「蕎麦」とその5つの軸がまとめて取得され、カード表示される
5. 別ユーザーが同じ`/genres`を開いても、RLSの`genres_all_own`ポリシーにより、このユーザーの「蕎麦」は一切見えない(存在しないのと同じ扱い)

## 7. つまずきやすいポイント・よくある誤解

- **`axes(*)`という埋め込み取得は、外部キーが正しく貼られていて初めて動く**：`axes.genre_id references genres.id`という外部キー制約が[[supabase_schema_knowledge|前回のスキーマ]]で定義済みだからこそ、Supabaseが自動でJOIN方法を推測できる。
- **`RequireAuth`の中で`loading`を無視すると、一瞬だけ`/login`にリダイレクトされることがある**：[[auth_knowledge|前回]]と同じ理由で、Supabaseへの問い合わせが終わるまでは「読み込み中」を表示し、判定を保留する必要がある。
- **軸の削除ボタンを3個ちょうどのときに押せてしまうと、DBには保存できるがレーダーチャートが崩れる**：UI側で`disabled={axisNames.length <= MIN_AXES}`として、そもそも押せないようにしている。

## 8. 確認問題

1. なぜ評価軸の数を「2個以下」ではなく「3個以上」に制限したのか、幾何学的な理由を説明せよ。
   - 解答例: レーダーチャートは軸の数だけ頂点を持つ多角形として描画するため、頂点が2個以下だと面積のある多角形にならない(1個は点、2個は線分)。3個以上あって初めて「多角形」として意味を持つため。
2. `axes`テーブルへのINSERTが失敗したとき、コードはどのような後片付けをしているか。
   - 解答例: 直前に作成した`genres`の行を`delete`で削除し、軸を持たない中途半端なジャンルが残らないようにしている。
3. `RequireAuth`を導入する前と後で、新しく保護ページ(例:「記録一覧」画面)を追加する手間はどう変わるか。
   - 解答例: 導入前は各ページに毎回ログイン判定のコードを書く必要があったが、導入後は`App.tsx`の`<Route element={<RequireAuth />}>`の内側にルートを1行追加するだけでよくなった。
